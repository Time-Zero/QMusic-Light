# 2026-10-30

## 动画渲染 GPU 化方案（QMusic Light）

- 产出 `docs/animation-gpu-migration.md`：现状盘点（15 个关键帧 / 33 处 transition）+ 瓶颈定位（B1-B6）+ 目标帧率与设备范围 + 四层实现思路 + 验证口径。
- 关键结论：入场动画本来就是 transform/opacity，已在合成层；真正的瓶颈是三条 CPU 路径：
  1. 进度条/音量条用 `width`、`left` 驱动（`ProgressBar.tsx:71,73`、`PlayerBar.tsx:240,243`）→ 布局 + 重绘，且 `timeupdate` 约 4 Hz 导致视觉步进；
  2. `currentTime` 4 Hz 写入 zustand → 整棵 PlayerBar / NowPlaying（含 100+ 歌词行）重渲染（`player-store.ts:273`）；
  3. `box-shadow` / `background` 过渡在 `.player`（fixed + 大阴影）容器内重绘。
- 附带发现：`components.css:704` 的 `.live` 选择器是死代码（CSS/TSX 均无该类）；`ProgressBar.positionToValue` 每次 pointermove 读 `getBoundingClientRect`（强制同步布局）；全仓无 `will-change`。
- 方案要点：单 rAF 驱动 + `--p` CSS 变量 + `scaleX`/`translate3d`；`timeupdate` 降频到 1 Hz 只喂文本；歌词列表改 transform 位移替代 `scrollIntoView` smooth；`data-motion` 三档降级（full/lite/off）。
- 验证门槛：稳态 10s 内 Layout count = 0、LoAF = 0、主线程每帧 < 2ms、GPU ≤ 30MB。

## 实施完成（同日）

新增 6 个模块：
- `shared/lib/progress-driver.ts`：单 rAF 循环 + 时钟外推，`estimateSeconds` 抽成纯函数可测；顺带维护 `html[data-playing]` 给 will-change 挂载。
- `shared/lib/motion-mode.ts`：`full|lite|legacy` 三档 → `<html data-motion>`；`watchFrameBudget()` 启动 4s 后采样 60 帧，p95>24ms 且慢帧≥15% 才降档。
- `shared/hooks/useRailWidth.ts`：ResizeObserver → `--rail-w`，逐帧不读 clientWidth。
- `shared/lib/perf-probe.ts`：`probeFrames()`，DEV 挂 `window.__qmusicProbe`。
- `features/player/TrackTime.tsx`：整秒订阅，把播放条从每秒渲染里摘出。
- `progress-driver.test.ts`：6 条用例。

关键实现决策（踩过的坑）：
- 旋钮定位 `transform: translate3d(calc(var(--p) * var(--rail-w) - 50%), -50%, 0)`，px 与 % 混算合法，无头 Chrome 实测通过；不能用 left:%（布局）。
- 歌词跟随：`scrollTop` 瞬移 + 反向 `translate3d(next - from)` 补间到 0。**符号是 next−from，写反会让内容朝反方向滑**。必须同时移除 `.np-lyrics` 的 `scroll-behavior: smooth`。
- `.track` 悬停底色并入 `::after` 时，伪元素会盖住文字 → 需 `isolation: isolate` + `z-index: -1`。
- `.vbar` 不能加 `contain: paint`（旋钮比条高会被裁）；只有 `.rail`（overflow hidden）可以。
- ProgressBar 去掉 `value` prop，`aria-valuenow` 由订阅回调按整秒写，否则为了实现无障碍又把组件拖回每秒渲染。

校验：typecheck 通过；43 tests passed；build 通过；无头 Chrome 实测 full/lite 两档计算样式落点一致（269px 轨上 knob x=102.2，lite 下 left=107.188px）。
